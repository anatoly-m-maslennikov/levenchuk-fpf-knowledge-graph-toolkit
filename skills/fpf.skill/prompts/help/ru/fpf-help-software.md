# Справка `$fpf` — Разработка ПО

Используйте эту область для DDD и ограниченных контекстов, бизнес-логики, требований и приёмки, TDD, качества кода, архитектуры ПО, интерфейсов и миграций, а также доказательств готовности к выпуску.

## Типичные профили

- DDD и ограниченные контексты
- Бизнес-логика и поведение предметной области
- Требования и приёмка
- Разработка через тестирование
- Качество кода
- Архитектура ПО
- Интерфейсы, зависимости и миграции
- Доказательства и гейты выпуска

## Типичные вызовы

Канонические идентификаторы команд остаются английскими; русские команды — их псевдонимы.

- `$fpf problem frame Сформулируй проблему функции, требования и границу приёмки.` — псевдоним: `рамка проблемы`.
- `$fpf structure recover Построй карту текущих ограниченных контекстов и бизнес-правил.` — псевдоним: `восстановить структуру`.
- `$fpf applicability scan Найди ограниченный набор паттернов FPF для этого вопроса о ПО.` — псевдоним: `скан применимости`.
- `$fpf sota harvest Построй карту актуальных данных для этой инженерной проблемы.` — псевдоним: `обзор исследований`.
- `$fpf options explore Сравни кандидаты архитектуры ПО без выбора победителя.` — псевдоним: `исследовать варианты`.
- `$fpf evaluation design Определи стратегию тестирования TDD или оценку качества кода.` — псевдоним: `дизайн оценки`.
- `$fpf design challenge Проверь предлагаемую миграцию API до реализации.` — псевдоним: `проверка дизайна`.
- `$fpf decision synthesize Выбери из оценённых альтернатив ПО и зафиксируй решение.` — псевдоним: `синтез решения`.
- `$fpf quality improve Улучши версионированный модуль и повтори оценку.` — псевдоним: `улучшение качества`.
- `$fpf alignment audit Проверь реализацию по принятой архитектуре и проверкам выпуска.` — псевдоним: `аудит согласованности`.

Профиль определяет предмет, а команда — аналитическое намерение. Слова «DDD», «TDD» или «архитектура» сами по себе не выбирают между восстановлением, проектированием, улучшением и аудитом.
