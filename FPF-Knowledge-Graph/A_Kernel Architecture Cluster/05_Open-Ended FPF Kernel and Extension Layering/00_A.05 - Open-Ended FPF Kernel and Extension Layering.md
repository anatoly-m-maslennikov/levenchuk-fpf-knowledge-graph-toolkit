## [[A_Kernel Architecture Cluster/05_Open-Ended FPF Kernel and Extension Layering/00_A.05 - Open-Ended FPF Kernel and Extension Layering|A.5]]:1 - Problem frame

FPF helps practitioners combine shared conceptual grounds and reusable methods with suitable domain methods.
FPF can support that use across changing disciplines only if it:

* **(i)** remains *stable* and *self‑consistent* over multi‑decade timespans;
* **(ii)** *invites*, rather than resists, the continual influx of new disciplinary knowledge; and
* **(iii)** allows multiple, even competing, explanatory lenses to coexist without forcing a “winner‑takes‑all” unification.

Different domains can require different assumptions and laws. Making a domain-specific assumption an unconditional Kernel commitment would impose it on uses where it may not hold and make those uses depend on its revision. Place domain-specific knowledge in extensions by default, with its applicability stated. Use **[[A_Kernel Architecture Cluster/08_Universal Core Principle- Test a U-Kind Across Domains/00_A.08 - Universal Core Principle- Test a U-Kind Across Domains|A.8]]** to test a U-kind’s cross-domain contribution and **[[A_Kernel Architecture Cluster/11_Ontological Parsimony/00_A.11 - Ontological Parsimony|A.11]]** to test whether a new ontological value is needed. The declaration rules in **[[A_Kernel Architecture Cluster/05_Open-Ended FPF Kernel and Extension Layering/00_A.05 - Open-Ended FPF Kernel and Extension Layering|A.5]]:4** expose dependencies so that a changed declaration can be followed to the uses that rely on it.

## [[A_Kernel Architecture Cluster/05_Open-Ended FPF Kernel and Extension Layering/00_A.05 - Open-Ended FPF Kernel and Extension Layering|A.5]]:2 - Problem

If FPF were to let **domain‑specific primitives creep into its Kernel**, two pathologies would follow:

| Pathology               | Manifestation                                                                                                                  | Breach of Constitution                                                     |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| **Kernel Bloat**        | Adding domain-specific root U-kinds or local type vocabularies to the Kernel increases its size and review burden.       | Violates **C-5 Ontological Parsimony**; erodes **P-1 Cognitive Elegance**. |
| **Conceptual Gridlock** | Conflicting axioms (deterministic thermodynamics vs. indeterministic econ‑metrics) must fight for space in the same namespace. | Breaks **C‑3 Cross‑Scale Consistency**; triggers chronic DRR deadlock.     |

A *minimal, extensible* design is therefore mandatory.

## [[A_Kernel Architecture Cluster/05_Open-Ended FPF Kernel and Extension Layering/00_A.05 - Open-Ended FPF Kernel and Extension Layering|A.5]]:3 - Forces

| Force                            | Tension                                                                                                                  |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **Stability vs. Evolvability**   | Stable core needed for trust ↔ constant domain innovation needed for relevance.                                       |
| **Universality vs. Specificity** | Single kernel language ↔ rich disciplinary idioms.                     |
| **Parsimony vs. Coverage**       | Few primitives keep reasoning elegant ↔ framework must still model energy budgets, epistemic uncertainty, agentic goals. |

## [[A_Kernel Architecture Cluster/05_Open-Ended FPF Kernel and Extension Layering/00_A.05 - Open-Ended FPF Kernel and Extension Layering|A.5]]:4 - Solution

FPF’s modularity is **declarative**, not “callable”: pattern texts publish **law‑governed declarations** (vocabulary + laws + applicability) that can be reused and specialised.

To keep the Kernel open‑ended, use the following boundary rules:

1. **Kernel minimality (C‑5).** Domain knowledge stays outside the Kernel by default; it enters as extension vocabularies and laws.
2. **Boundary packaging via `U.Signature` ([[A_Kernel Architecture Cluster/06_Signature Stack- Classify and Place Boundary Claims/05_A.06.00 - U.Signature - Reusable Law-Governed Declaration Episteme|A.6.0]]).** For reusable declaration bundles admitted as signatures under **[[A_Kernel Architecture Cluster/06_Signature Stack- Classify and Place Boundary Claims/05_A.06.00 - U.Signature - Reusable Law-Governed Declaration Episteme|A.6.0]]**, expose actual declaration dependencies in an explicit `SignatureManifest` (`imports`, `provides`).
3. **Dependency vs specialisation are separate relations.** `imports` forms a dependency DAG constrained by **[[E_The FPF Constitution and Authoring Guides/04_05_Four Guard-Rails of FPF/03_E.05.03 - Unidirectional Dependency between FPF Families|E.5.3]]**; refinement/extension (`⊑`, `⊑⁺`) is expressed separately (for mechanism declarations, see **[[A_Kernel Architecture Cluster/06_Signature Stack- Classify and Place Boundary Claims/06_A.06.01 - U.Mechanism - Reusable Law-Governed Operation Declaration|A.6.1]]:4.8**; use **[[C_Kernel Extension Specifications/17_29_Mathematical Lens Use/00_C.29 - Mathematical Lens Use|C.29]]** when a mathematical morphism is claimed) and should not be conflated with `imports`.
4. **Registry references stay references.** Bridge ids, policy‑ids, and edition‑ids (Part F) are registry identifiers: they are cited/pinned where needed, not treated as exported symbols in `provides`.
